# Автоматизация заказов портала

Сценарий работает в существующем Flask-приложении: форма готовой услуги → заказ в БД → персональная ссылка Robokassa → письмо клиенту → подтверждение оплаты серверным ResultURL → письмо о подтверждении. GigaChat, другие модели и отдельный сервер n8n для этой цепочки не требуются.

## Что происходит

- Сумма и название берутся из каталога на сервере и сохраняются в заказе. Покупатель не задаёт цену. Для услуг «от …» остаётся согласование стоимости через заявку.
- Новая форма имеет ключ оформления. Повторная отправка той же формы с теми же данными возвращает тот же заказ; изменение данных с прежним ключом отклоняется. Старую, открытую до обновления страницу надо перезагрузить.
- `/orders/pay/<случайный-токен>/` открывает существующий заказ. Переходы по ссылке не создают новые счета. Сумма в ссылке и чеке соответствует сохранённому заказу даже после изменения каталога.
- Режим TEST/LIVE сохраняется при оформлении. Ссылка не переводится незаметно из тестового режима в боевой при изменении настройки магазина.
- Только проверенное серверное уведомление Robokassa меняет статус оплаты. Браузерные SuccessURL/FailURL служат для отображения результата. Повтор ResultURL не создаёт повторное письмо и не отменяет состояние возврата.
- Очередь писем хранится в `order_notifications`, снимок оформления — в `order_checkouts`. При старте `db.create_all()` создаёт эти новые таблицы без изменения столбцов прежней таблицы `orders`. Старые заказы не обрабатываются задним числом.

Платёжная ссылка даёт доступ к конкретному заказу. Не публикуйте её токен, не прикладывайте его к открытым скриншотам и не записывайте в прикладные журналы. В настройках прокси также следует исключить полные пути `/orders/pay/…` из access-log либо маскировать токены.

## Настройка на сервере

Сначала проверить и объединить PR с автоматизацией. Push в `main` запускает существующий деплой; не объединять изменение, пока тесты не пройдены. Дождаться успешного развёртывания приложения. Перед изменением рабочего окружения сохранить резервную копию БД и файла конфигурации вне репозитория.

Секреты вводятся только в серверный `/srv/st8dom/.env`. Не отправлять пароль SMTP в чат, GitHub, команды с историей или скриншоты.

Для SMTP с STARTTLS:

```dotenv
ORDER_EMAIL_ENABLED=1
SITE_URL=https://st8dom.ru
SMTP_HOST=адрес_сервера_вашей_почты
SMTP_PORT=587
SMTP_USERNAME=ваш_полный_email
SMTP_PASSWORD=пароль_приложения
SMTP_FROM=ваш_полный_email
SMTP_USE_TLS=1
SMTP_USE_SSL=0
```

Для SMTP с TLS с начала соединения, например на порту 465, вместо трёх соответствующих значений использовать:

```dotenv
SMTP_PORT=465
SMTP_USE_TLS=0
SMTP_USE_SSL=1
```

Для писем по заказам должен быть включён ровно один режим: `SMTP_USE_TLS` или `SMTP_USE_SSL`. Соединение проверяет сертификат сервера. Не менять существующие пароли и ResultURL Robokassa ради включения писем. По умолчанию `ORDER_EMAIL_ENABLED` выключен: без разрешения отправки и настроенной почты письма остаются в очереди.

Если Compose передаёт приложение через `env_file: .env`, после правки окружения пересоздать контейнер:

```bash
docker compose --project-directory /srv/st8dom up -d --no-deps app
docker compose --project-directory /srv/st8dom exec -T app flask order-email-status
```

Если Compose перечисляет переменные явно в `environment`, добавить туда новые настройки тоже. Не выводить `docker compose config` или полный `docker inspect` в чат: они могут содержать секреты. Команда `order-email-status` выводит только признаки готовности и количества сообщений.

### Автоматический обработчик писем

Установщик предназначен для VPS с systemd и Docker Compose. Он обнаруживает путь к Docker, проверяет запущенный сервис `app`, создаёт только два собственных unit-файла и включает таймер. Платежи и возвраты он не создаёт. При включённой отправке запуск таймера разрешает обработку уже накопившейся очереди новых заказов — сначала проверить её в админке.

Выполнять на VPS после проверки PR и успешного деплоя:

```bash
docker compose --project-directory /srv/st8dom exec -T app cat /app/deploy/install-order-notifications.sh > /tmp/st8dom-install-order-notifications.sh
less /tmp/st8dom-install-order-notifications.sh
sudo bash /tmp/st8dom-install-order-notifications.sh install
```

Таймер запускает `flask order-notifications --limit 5` в работающем контейнере примерно через минуту после завершения предыдущего прохода. Отдельный контейнер и доступ к секретам из GitHub не добавляются. После обновления образа используется тот же сервис `app`.

Проверка и отключение:

```bash
sudo bash /tmp/st8dom-install-order-notifications.sh status
sudo bash /tmp/st8dom-install-order-notifications.sh remove
```

Отключение сохраняет БД и очередь. Уже начавшаяся отправка может завершиться; установщик не прерывает SMTP посередине. Для разовой обработки после осознанного включения почты:

```bash
docker compose --project-directory /srv/st8dom exec -T app flask order-notifications --limit 5
```

## Ошибки и повторы

| Состояние письма | Значение и действие |
| --- | --- |
| `pending` | Ожидает обработчика или следующей допустимой попытки. Нет SMTP/отправка выключена — не теряется. |
| `sending` | Конкретный обработчик захватил событие. Другой обработчик его не отправляет. |
| `sent` | Почтовый сервер принял письмо. Это ещё не доказательство попадания во «Входящие». |
| `failed` | SMTP явно не принял письмо, допустимые попытки исчерпаны либо отсутствует снимок заказа. Проверить настройку и причину в админке. |
| `unknown` | Ответ SMTP неоднозначен или процесс оборвался после захвата. Сначала проверить почту получателя и журналы провайдера. Автоматической повторной отправки нет. |
| `cancelled` | Событие больше не требуется, например ссылка на оплату после подтверждённой оплаты. |

Для явного отказа, при котором известно, что SMTP не принял письмо, предусмотрено не более трёх попыток с задержкой. Ошибка после начала передачи с неизвестным результатом не повторяется вслепую. Сбой закрытия SMTP после положительного ответа не отменяет факт принятия письма. Остановка процесса после принятия SMTP, но до записи результата в БД, потребует ручной сверки; гарантии «ровно один раз» для SMTP нет.

Исходящие сообщения ограничены: до 100 в сутки в целом и до 6 на один адрес; при достижении предела очередь откладывается. Статус заказа хранится отдельно от доставки: ошибка почты не превращает заказ в оплаченный и не удаляет его.

## Проверка перед использованием

1. Запустить тесты из PR: оформление/дубликат/конфликт; неизменная сумма сохранённого заказа; недействительная ссылка; смена TEST/LIVE; правильная и неверная подпись; повтор callback после оплаты и возврата; ошибки SMTP и неопределённый результат.
2. На сервере `order-email-status` должен показать включённую отправку и готовую почту. В админке не должно быть непроверенной очереди, которую не планировалось отправлять.
3. Создать новый заказ с выдуманным именем и собственным тестовым почтовым адресом. Проверить один заказ в БД и письмо с соответствующей ссылкой. Проверить «Входящие» и «Спам». Реально оплачивать заказ для этой проверки не требуется.
4. Открыть ссылку повторно: номер и сумма остаются прежними. Сопоставить сумму на странице с каталогом и сохранённым заказом. Не переходить к списанию средств ради проверки писем.
5. Подтверждение оплаты проверять синтетическим подписанным callback только в изолированных тестах либо официальным тестовым режимом Robokassa. Не отправлять поддельный callback в боевую БД и не менять глобальный режим рабочего магазина без отдельного плана.
6. Отдельно зафиксировать результат реальной доставки: SMTP «принято» и письмо во «Входящих» — разные проверки. До этой проверки не объявлять почтовую автоматизацию полностью запущенной.

Возврат исторической проверочной оплаты на 10 ₽ в эту автоматизацию не входит. Он не повторяется при установке, запуске таймера, открытии ссылки или обработке очереди.
