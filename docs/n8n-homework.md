# NNS_09 — заявка, ИИ, таблица, Robokassa и уведомление

Выбран **вариант 2 домашнего задания**: адаптация под реальный процесс портала ДИС. Это отдельная форма n8n с двумя готовыми услугами. Работающая форма портала и её автоматизация сохраняются.

Рабочее имя сценария: **NNS_09 — ДИС: заявка → ИИ → таблица → Robokassa → email**.

## Что подготовлено и что ещё проверить

Подготовлен импортируемый JSON, шаблон колонок и локальные проверки логики. В этой поставке **не выполнены импорт и реальный запуск в пользовательском n8n**. Нет выдуманных исполнений, закреплённых ответов модели или реальных ключей. После импорта нужно выбрать credentials и таблицу; API заказов должен быть развёрнут и включён на портале.

Уведомление доставляет уже работающая SMTP-очередь портала. Узел «Email — уведомить клиента» делает явный HTTP-запрос постановки письма в эту очередь. Второй SMTP-узел n8n добавлять не требуется: это создало бы двух отправителей одного письма. В варианте 2 ДЗ канал уведомления остаётся электронной почтой.

## Процесс для сдачи ДЗ

На портале продаются готовые услуги. Для экспресс-разбора предусмотрена цена 4 900 ₽, для AI-аудита процесса — 14 900 ₽. В учебной форме n8n клиент указывает имя, контакт, email, услугу, сумму и комментарий.

Сценарий проверяет поля и фиксированную цену, передаёт имя, услугу, сумму и комментарий ИИ, проверяет структурированный JSON, сохраняет заявку в Data Table, получает заказ и платёжную ссылку от портала и ставит персональное письмо в очередь. Сумма контролируется программными правилами и каталогом портала. ИИ готовит описание и приоритет.

Путь выполнения:

1. «Форма заявки» — шесть полей задания.
2. «Проверить форму» — обязательные данные, email, цена и ограничения длины.
3. «ID заявки» — SHA256 исходных нормализованных данных и времени отправки.
4. «ИИ — обработать заявку» — OpenRouter, модель OpenAI GPT-4.1 Mini.
5. «Проверить JSON ИИ» — ровно шесть полей; имя, услуга и сумма совпадают с формой.
6. «Таблица — сохранить заявку» — upsert по request_id, статус «Формируется ссылка».
7. «Robokassa — создать ссылку» — защищённый API портала, без списания денег.
8. «Проверить платёжную ссылку» — номер, сумма, услуга и адрес соответствуют заявке.
9. «Таблица — сохранить ссылку» — номер заказа, ссылка, финансовый статус.
10. «Email — уведомить клиента» — идемпотентная постановка письма в очередь портала.
11. «Проверить постановку письма» — отличает очередь от принятия письма SMTP.
12. «Таблица — статус письма» — сохраняет фактическое состояние уведомления.
13. «Заявка принята» — завершает форму и показывает проверенную ссылку.

Публичная форма не принимает произвольные услуги или суммы. Для других задач используется обычная форма связи и ручное согласование цены.

## 1. Подготовить портал

Эта часть выполняется после развёртывания backend из той же поставки.

В серверном окружении нужно установить отдельный **N8N_ORDERS_API_TOKEN** длиной не менее 32 символов, затем пересоздать контейнер приложения. Значение вводится локально на сервере и в n8n Credentials. В workflow нет паролей Robokassa, SMTP или администратора. При отсутствии токена API выключен.

Используются маршруты:

- POST https://st8dom.ru/api/automation/orders/ — создать или вернуть тот же заказ по request_id.
- GET https://st8dom.ru/api/automation/orders/<request_id>/ — прочитать заказ и состояние уведомления.
- POST https://st8dom.ru/api/automation/orders/<request_id>/notify/ с JSON {} — поставить первое письмо в очередь один раз.

Заголовок авторизации: Authorization: Bearer <N8N_ORDERS_API_TOKEN>.

Первый POST сам письмо не отправляет. Второй POST /notify/ передаёт это действие очереди портала. Полный результат требует работающего таймера уведомлений на сервере. Проверка авторизации SMTP и работа таймера были выполнены ранее для формы портала; отдельный n8n-путь нужно проверить после импорта.

## 2. Импортировать workflow

1. Открыть новый workflow NNS_09.
2. В меню workflow выбрать Import from File.
3. Выбрать workflows/NNS_09_DIS_Robokassa.json.
4. Сохранить сценарий. Он подготовлен выключенным: сначала настройка и тест.
5. Если импорт создал новый workflow, оставить один нужный сценарий; прежние рабочие workflow не удалять.

Три цветных заметки на схеме показывают настройки: ИИ, таблица, API портала.

## 3. Выбрать credential OpenRouter

В узле «ИИ — обработать заявку» открыть Authentication:

- Generic Credential Type → Header Auth.
- Создать или выбрать credential с именем OpenRouter — NNS_09.
- Name: Authorization.
- Value: Bearer <ваш ключ OpenRouter>.

Значение ключа вводится только в credential. В JSON-экспорт его не вставляют.

Модель задана как openai/gpt-4.1-mini. Запрос использует response_format с JSON Schema, strict: true и provider.require_parameters: true. Ответ снова проверяется кодом: несовпадение суммы, неправильные поля, ссылки или HTML останавливают цепочку до создания заказа.

Если ИИ вернул 401/402, проверить credential или доступный баланс провайдера. Если ответ 400 относится к response_format, проверить поддержку структурированных ответов выбранным endpoint; не заменять проверку JSON фиктивным ответом.

## 4. Создать таблицу

Рекомендуемое имя Data Table: **NNS_09_orders**.

Файл workflows/NNS_09_table.csv содержит только заголовок без фиктивных заявок. Некоторые версии n8n не импортируют CSV без строк данных. В таком случае создать таблицу вручную — заполнять её примером ради успешного импорта не нужно.

Создать все колонки с типом **String**:

| Колонка | Значение |
|---|---|
| request_id | Стабильный ключ заявки |
| date | Время отправки формы, ISO |
| client_name | Имя клиента |
| contact | Телефон или никнейм |
| email | Электронная почта |
| product_slug | Код услуги |
| request_type | Название выбранной услуги |
| request_summary | Краткое описание заявки от ИИ |
| payment_description | Описание услуги для оплаты |
| amount | Сумма с двумя знаками |
| priority | low, normal или high |
| status | Состояние оформления или оплаты |
| payment_link | Персональная ссылка на заказ |
| order_id | Номер заказа портала |
| notification_status | Состояние письма |

Во **всех трёх узлах «Таблица»** выбрать одну и ту же таблицу вместо SELECT_TABLE_ID. После выбора проверить раздел Columns: поля должны соответствовать английским названиям колонок выше.

Первый узел выполняет Upsert по условию request_id Equals request_id из проверенной заявки. Два последующих — Update по тому же ключу. Системные колонки id/createdAt/updatedAt n8n создаёт самостоятельно.

Сумма и номер сохранены как строки, чтобы избежать ошибок преобразования и сохранить точный денежный формат. Для первой новой заявки после получения ссылки status должен стать «Ожидает оплату».

## 5. Выбрать credential портала

В обоих узлах «Robokassa — создать ссылку» и «Email — уведомить клиента»:

- Authentication: Generic Credential Type → Header Auth.
- Credential: ДИС — API заказов NNS_09.
- Name: Authorization.
- Value: Bearer <N8N_ORDERS_API_TOKEN>.

Оба узла используют один и тот же отдельный токен API. Адрес портала уже задан. Пароль #1 Robokassa переносить в n8n не требуется.

## 6. Выполнить один учебный запуск

Нажать **Execute Workflow**, затем открыть **Test URL** узла «Форма заявки». Execute Step у одного триггера проверяет только триггер; для всей цепочки запускать workflow.

Заполнить форму:

| Поле | Учебный пример |
|---|---|
| Имя | Тест-ДИС |
| Контакт | @test_dis |
| Электронная почта | Собственный адрес — вводится локально |
| Услуга | Экспресс-разбор |
| Сумма | 4900 |
| Комментарий клиента | Нужно упростить обработку обращений и определить следующие шаги. |

Для AI-аудита процесса сумма должна быть 14900. Другие значения намеренно отклоняются.

После отправки проверить:

1. Узел ИИ получил реальный ответ провайдера.
2. «Проверить JSON ИИ» вернул ровно согласованный анализ.
3. В Data Table появилась одна строка с тем же request_id.
4. API портала вернул номер нового заказа и payment_link.
5. В таблице появились ссылка и статус «Ожидает оплату».
6. Уведомление получило pending/sending либо sent. pending означает очередь; sent означает принятие SMTP, а не доказательство доставки во «Входящие».
7. Через 1–2 минуты письмо пришло на собственный адрес. Проверить «Спам».
8. Ссылка из письма открывает тот же номер заказа и сумму. Реально оплачивать учебный заказ не нужно.

Нельзя выдавать старый заказ №8 за результат нового сценария n8n. Он подтверждает ранее проверенный путь портала; для ДЗ нужен запуск этой цепочки с новым номером.

В Production URL поток запускается после сохранения и включения/публикации workflow. Если используется локальный n8n, для удалённых посетителей нужен действующий внешний адрес, например уже используемый ngrok. Для локальной учебной проверки достаточно открытого Test URL.

Если Test URL всё ещё показывает старый отключённый ngrok, это настройка адреса экземпляра n8n (например WEBHOOK_URL), а не ошибка JSON. Для локальной проверки открыть соответствующий путь формы на localhost:5678. Не менять глобальное окружение вслепую: оно может использоваться другими workflow. Фактическая версия установленного n8n и его Test URL в этой поставке не проверены; наличие Data Tables подтверждено пользовательским экраном.

## Ошибки и повторный запуск

- Ошибка формы или ответа ИИ останавливает сценарий до создания финансового заказа.
- Ошибка после записи таблицы сохраняет строку для проверки; после создания заказа портал сохраняет его независимо от состояния n8n.
- request_id определяется нормализованными данными исходной формы вместе с submittedAt. При повторе **того же исполнения с исходными данными** ключ сохраняется, API возвращает прежний заказ.
- Новая отправка формы с новым submittedAt — новая заявка, даже если имя и услуга одинаковые.
- Для восстановления не перепечатывать время отправки вручную. Использовать исходные данные неудачного исполнения.
- Data Table не является финансовым источником истины или распределённой блокировкой: идемпотентность создания заказа и постановки письма обеспечивает портал.
- При failed/unknown/cancelled уведомления сценарий останавливается и не объявляет письмо отправленным. Сначала проверить заказ и журнал портала. Не добавлять автоматический повтор SMTP после неизвестного результата.
- Повтор /notify/ не создаёт второе сообщение. Состояние sent означает, что старое уведомление уже принято SMTP.
- При смене статуса заказа между созданием ссылки и уведомлением workflow останавливается для сверки.
- Полное повторное выполнение после уже состоявшейся оплаты не предназначено для выдачи новой ссылки: фактический статус берётся с портала; запрет лишнего уведомления должен сохраниться.
- В экспорт не добавлены автоматические retries для HTTP; условия восстановления контролируются по сохранённым данным.
